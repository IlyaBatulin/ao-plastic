## Обновление: выбран экономичный вариант без полного Supabase

Пользователь выбрал текущий сервер REG.RU в Москве: 3 vCPU, 3 ГБ RAM, 40 ГБ.

Предыдущие разделы о self-hosted Supabase ниже — альтернативный план, НЕ текущая
инструкция развёртывания. Для обычного PostgreSQL нужно переписать слой доступа
и авторизацию; простая смена NEXT_PUBLIC_SUPABASE_URL не подходит.

На 80.78.241.35 установлен PostgreSQL 18.6 из штатного репозитория Ubuntu 26.04.
Создана пустая aoplastic_staging; источник остаётся PostgreSQL 17.6 в Supabase.
Логическое восстановление в более новую версию требует проверки расширений,
Supabase-специфичных схем и отдельного теста, автоматическая совместимость не заявляется.
Не переносить служебные схемы Supabase в vanilla PostgreSQL вслепую.

- nginx и PostgreSQL active; Next.js отвечает 307 на закрытую паролем страницу.
- Вход root по существующему локальному SSH-ключу настроен и проверен.
- Сайт /var/www/ao-plastic, git HEAD 25e84a7, есть существующий untracked etc:
  не удалять/не перезаписывать. PM2/nginx не перезапускались, reboot не выполнялся.

Блокер экспорта: нет защищённой строки подключения к исходному PostgreSQL.
Сохранить SOURCE_DATABASE_URL в локальный .env.migration.local (исключён из Git
правилом .env*); не присылать пароль в чат. API/MCP не заменяет полный дамп.
Само подключение целевой БД к сайту, перенос Auth, бэкапы вне сервера и сверка
пока НЕ выполнены. Присланный в чат SSH-пароль сменить после настройки ключа.
Проверить доступность исходной базы на сетевом уровне после появления строки
подключения, затем сделать экспорт. Сам пароль не включать в аргументы процессов,
Git, журнал сервера или текст отчёта.

Полный self-hosted Supabase требует по официальной документации минимум 4 ГБ RAM;
сейчас доступно 3 ГБ. Документация допускает исключение ненужных сервисов
(Realtime, Storage, imgproxy, Edge Runtime), но экономичная конфигурация
должна быть испытана на этом сервере отдельно, прежде чем использовать её
для клиентов. Обычный PostgreSQL уже подготовлен; он НЕ реализует Supabase
Auth, PostgREST и существующие вызовы клиента. Выбор между минимальным
совместимым стеком и переписыванием приложения остаётся архитектурным этапом,
а не шагом замены переменной окружения. У источника нет объектов Supabase Storage,
поэтому покупка S3-хранилища для исходных объектов сейчас не требуется;
файлы public/uploads на действующем сайте учитываются отдельно.

## Что переносить кроме public

- Auth: пользователи и связанные записи; сохраняем работающий сервис авторизации.
- Роли, права, политики RLS, функции, триггеры, последовательности, представления.
- Проверенная версия приложения и локальные данные каталога: data/products.json,
  файлы fallback и редакционные исправления. Дамп не заменяет эти файлы.
- public/uploads с ДЕЙСТВУЮЩЕГО сервера: админка пишет туда локально.
  Подключить отдельный постоянный volume; не хранить загрузки только внутри контейнера.
- public/images, public/videos, public/docs и остальные используемые ресурсы.
- Настройки SMTP, редиректов Auth, уведомлений, доменов и секретов отдельно,
  через защищённый канал, не в Git и не в переписку.
- Storage сейчас пуст; повторить проверку перед финальным переносом.

## Требования к целевому окружению

Нужны адрес/SSH alias, пользователь для SSH, ОС, CPU/RAM/SSD, свободное место,
расположение сервера, способ запуска сайта и выбранный API-поддомен.
Неизвестные параметры не подменять предположениями.
Использовать официальный self-hosted Docker Compose с зафиксированным релизом,
PostgreSQL 17 и совместимыми версиями Auth/Storage; локальный supabase start
не является production-развёртыванием. Сверить расширения и служебные схемы.

Наружу — HTTPS API и сайт. PostgreSQL, pooler и внутренние сервисы — в закрытой
сети; Studio — через VPN/ограничение IP. Проверить опубликованные Docker-порты
извне, не полагаться только на правила UFW. Уникальные секреты, SSH-ключи,
постоянные volumes, мониторинг диска и состояния сервисов обязательны.

На текущем компьютере Docker CLI установлен, но Linux engine не запущен.
psql и Supabase CLI в PATH не обнаружены. Ничего автоматически не установлено.

## Порядок выполнения

1. Получить параметры сервера, доступ по SSH и согласовать окно переключения,
   допустимую потерю данных (RPO), время восстановления (RTO), хранение копий.
2. Проверить сервер без изменений. Зафиксировать текущие volumes, порты и сервисы,
   чтобы не затронуть существующие приложения. Подготовить отдельное окружение.
3. Получить защищённое подключение к исходной БД; проверить версии CLI и команды
   через --help. Сделать полный совместимый экспорт ролей, схемы и данных по
   официальному руководству Supabase, а не public-only pg_dump.
4. Сохранить дамп и файлы вне Git, ограничить доступ, зашифровать внешнюю копию,
   записать контрольные суммы. Не печатать connection string, хеши паролей,
   содержимое пользовательских таблиц и секреты в отчёты.
5. Пробно восстановить в ПУСТОЕ тестовое окружение. При несовместимости схем
   подобрать версии/проверенные преобразования; не удалять непонятные COPY-блоки
   ради успешного завершения. Сверить точные количества строк, ключи, constraints,
   sequences, расширения, функции, политики и права.
6. Подключить тестовую копию сайта: новые env, разрешённый API-origin в CSP,
   remotePatterns при необходимости, Auth URL/SMTP. Пересобрать Next.js:
   NEXT_PUBLIC_* встраиваются в клиент при сборке. Не раскрывать service_role.
7. Выполнить приёмку ниже. Тестовые письма и Telegram направлять в тестовые каналы.
8. Остановить ВСЕ записи в исходную систему: формы, админку, регистрацию,
   фоновые интеграции. SITE_PASSWORD сам по себе не гарантирует остановку записей.
   Снять согласованный финальный снимок БД и файлов, восстановить и сверить.
9. Переключить приложение; не допускать двух одновременно пишущих систем.
   Проверить каталог, Auth, права и заказ, только затем открыть запись.
10. Сохранить старую систему изолированной/read-only на согласованный срок.
    При откате после новых записей сначала сохранить и перенести новые заказы
    и изменения; простая смена URL может потерять данные.

## Приёмка — все пункты обязательны

- [ ] Точные счётчики всех переносимых таблиц сверены в согласованном снимке.
- [ ] Проверены внешние ключи, sequence и связи товаров с категориями.
- [ ] Карточки/таблицы ABS, УПЕКС 1–6, ПСВ-Л, ДМС, дисперсий открываются RU/EN.
- [ ] Изображения, документы, загрузки доступны и переживают перезапуск/деплой.
- [ ] Вход покупателя, восстановление пароля, SMTP; после смены JWT повторный вход.
- [ ] Пользователь A не читает/меняет данные B; anon не читает заказы/профили.
- [ ] Админка, загрузка фото, заказ, заявки, новости работают.
- [ ] Sitemap, CSP, HTTPS, canonical и индексируемость не регрессировали.
- [ ] Проверены автоматический бэкап и восстановление на отдельном окружении.
- [ ] Бэкап хранится вне основного сервера, настроены уведомления о сбое/месте.
- [ ] Зафиксированы версии, ответственный за обновления, RPO/RTO и план отката.
