# 🔒 Исправление предупреждений безопасности Supabase

## Обзор проблем

Supabase Security Advisor обнаружил несколько предупреждений в базе данных:

### 1. ⚠️ Function Search Path Mutable (8 предупреждений)

**Проблема:** Функции PostgreSQL не имеют установленного `search_path`, что может привести к уязвимости через подмену схемы (schema injection).

**Риск:** Средний. Если злоумышленник создаст функцию с таким же именем в другой схеме, ваша функция может выполниться с непредсказуемыми последствиями.

**Решение:** ✅ **ИСПРАВЛЕНО** — добавлен `SET search_path = public, pg_temp` во все функции.

**Затронутые функции:**
- `public.assign_manager_to_order`
- `public.fn_on_order_items_insert`
- `public.fn_audit`
- `public.fn_on_order_insert`
- `public.fn_orders_sanitize`
- `public.gc_webhook_events`
- `public.refresh_orders_summary`

### 2. ❌ Security Definer View (3 ошибки)

**Проблема:** Представления созданы с `SECURITY DEFINER`, что означает, что они выполняются с правами создателя, а не вызывающего пользователя.

**Риск:** Низкий-Средний. Если представления используются только для чтения публичных данных (категории, товары), это нормально. Но если они возвращают чувствительные данные, это может быть проблемой.

**Затронутые представления:**
- `public.v_categories_summary`
- `public.v_products_brief`
- `public.v_products_full`

**Решение:** 
- ✅ **Если представления используются только для чтения публичных данных** — это нормально, можно оставить.
- ⚠️ **Если нужно исправить:** удалите `SECURITY DEFINER` из определения представлений (но это может потребовать пересоздания представлений).

**Как проверить:**
```sql
SELECT 
    schemaname, 
    viewname, 
    definition 
FROM pg_views 
WHERE schemaname = 'public' 
  AND viewname IN ('v_categories_summary', 'v_products_brief', 'v_products_full');
```

### 3. ℹ️ Materialized View in API (1 информационное сообщение)

**Проблема:** Материализованное представление `mv_orders_summary` доступно через Data API Supabase.

**Риск:** Низкий. Это информационное сообщение. Если представление содержит только агрегированные данные без чувствительной информации, это нормально.

**Решение:** 
- ✅ **Если представление используется для аналитики** — можно оставить как есть.
- ⚠️ **Если нужно скрыть:** настройте RLS политики или исключите представление из публичного доступа.

## ✅ Применение исправлений

### Шаг 1: Применить миграцию для функций

Примените миграцию `007_fix_function_security.sql`:

1. Откройте Supabase Dashboard → SQL Editor
2. Скопируйте содержимое `migrations/007_fix_function_security.sql`
3. Выполните SQL запрос
4. Проверьте, что предупреждения исчезли

### Шаг 2: Проверка представлений (опционально)

Если хотите исправить предупреждения о представлениях:

1. Проверьте, используются ли представления в коде:
   ```bash
   grep -r "v_categories_summary\|v_products_brief\|v_products_full" app/
   ```

2. Если представления созданы автоматически Supabase, возможно, их нужно пересоздать без `SECURITY DEFINER`.

3. Если представления используются только для чтения публичных данных, можно оставить как есть.

### Шаг 3: Проверка материализованного представления (опционально)

Если `mv_orders_summary` содержит чувствительные данные:

1. Настройте RLS политики для материализованного представления
2. Или исключите его из публичного доступа через настройки Supabase

## 📊 Результат

После применения миграции `007_fix_function_security.sql`:

- ✅ 7 предупреждений "Function Search Path Mutable" должны исчезнуть
- ⚠️ 3 ошибки "Security Definer View" останутся (если представления используются для публичных данных, это нормально)
- ℹ️ 1 информационное сообщение "Materialized View in API" останется (не критично)

## 🔍 Проверка исправлений

После применения миграции проверьте в Supabase Dashboard → Security Advisor:

1. Количество предупреждений должно уменьшиться
2. Функции должны показывать "Function Search Path Set" вместо "Function Search Path Mutable"

## 📝 Примечания

- Все исправления безопасны для применения в production
- Миграция использует `CREATE OR REPLACE`, поэтому безопасна для повторного применения
- Функции с `SET search_path` работают так же, как и раньше, но теперь безопаснее
